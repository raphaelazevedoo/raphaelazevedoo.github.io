01 · Context and problem

One incorrect field could interrupt billing.

Sentry is an internal order management system covering logistics, inventory, billing and invoice issuance. Order information passes through several stages and integrations before an NF-e, Brazil's electronic fiscal invoice, is processed.

Incorrect customer details, incomplete addresses and invalid product tax data could cause invoice rejections. In some cases, finding and correcting the issue required technical or operational intervention, including manual data changes.

The challenge was to provide a correction workflow within the system: identify the problematic information, guide the edit and allow another processing attempt with validated data.

An issue observed during development

The fiscal integration rejected a request that lacked valid recipient identification. This showed that editable fields were only part of the solution: data validation and a clear explanation of the rejection were also needed before resubmission.

02 · The solution

Centralized corrections, from the order to the fiscal response.

The NF-e Editor brings together order lookup, editing of invoice data and resubmission to Focus NF-e. The interface lets operations staff follow the workflow instead of relying on a generic failure message.

Recipient and address

Editing of name or legal business name, identification, state tax registration, postal code, street, number, address complement, municipality and state. ViaCEP lookup helps populate address fields from the Brazilian postal code.

Product data

Correction of EAN product identifiers and NCM tax classification codes on order items, using each item's identifier to update the corresponding information.

Validation and resubmission

Required fields and invalid information are checked before submission. Once corrections are saved, the backend rebuilds the payload with the updated data and reuses the existing fiscal processing workflow.

Feedback and continuity

Loading, success and error states make progress visible. If an attempt fails, the form retains the entered data so users can make further corrections and try again.

03 · My contribution

Working across the interface, business logic and integration.

I contributed to the feature's full-stack development, working on parts of the interface and backend responsible for editing, validating, persisting and resubmitting invoice data.

  • Frontend: editor components and forms, interface state, typed data structures, endpoint consumption, validation and postal code lookup.
  • Backend: endpoints, DTOs, business rules, recipient and item updates, persistence and coordination of invoice resubmission.
  • Integrations: preparing data sent to Focus NF-e and interpreting responses to provide useful feedback to operations staff.
  • Diagnosis: investigating rejections and inconsistencies involving payloads, API contracts, database records and interface behavior.

This required following issues across layers. A failure visible in the form could originate in the endpoint contract, persisted data or the response from the fiscal service.

04 · Architecture and workflow

Saving a correction and processing an invoice are separate steps.

  1. Look up and editReact and Next.js load order data through the API and present the form. ViaCEP provides an auxiliary address lookup.
  2. Validate the requestThe interface checks fields, while NestJS validates the request contract and data through DTOs and business rules.
  3. Persist the changesThe order and its items are updated in PostgreSQL within a database transaction.
  4. Resubmit externallyAfter persistence completes, the service rebuilds the payload and uses the existing Focus NF-e integration workflow.
  5. Present the outcomeThe fiscal response is interpreted and shown in the interface, distinguishing saved corrections from the result of invoice processing.

A local transaction does not cover the success of an external API call. The workflow therefore separates what was persisted from what the fiscal service actually returned.

05 · Challenges and technical decisions

Consistency, contracts and the actual operation outcome.

1. Short transactions, integration after persistence

Order and item changes happen within the transaction. The external call follows that step, avoiding an open database transaction while waiting for the fiscal API.

This separation also makes it possible to clearly represent a situation where data was saved but resubmission failed. The application must guide the next action without implying that every step succeeded.

2. Typed contracts between frontend and backend

A concrete mismatch involved sending a product property that the backend DTO did not accept. NestJS validation rejected the payload and helped identify the discrepancy.

Aligning the contract brought the interface's submitted fields into agreement with the endpoint's accepted data. TypeScript and runtime validation play complementary roles in this workflow.

3. HTTP success does not mean the invoice was processed

The endpoint could save changes and respond successfully while invoice resubmission failed. The frontend was updated to consider the actual fiscal operation outcome alongside the HTTP status.

This supports accurate feedback: a successful data update must not hide an integration rejection.

4. Error messages that guide corrections

Response handling preserves relevant information returned by Focus NF-e, including specific rejection messages. The interface can retrieve these details to help the user understand what needs to change.

5. Preserving work after a failure

Keeping the form populated prevents users from re-entering every correction after an unsuccessful attempt. Error handling becomes part of the correction experience, alongside loading and confirmation states.

6. Traceability as a planned enhancement

The project description also covers an audit design with the responsible user, previous and updated values, changed fields, origin and a correlation identifier. This is a planned design enhancement, not a claim that complete auditing has already been implemented.

07 · Outcome and lessons

More autonomy to correct, more clarity to resubmit.

The reported outcome was the centralization of invoice data corrections in an operational interface, helping reduce rework, speed up the handling of rejections and reduce the need for direct technical intervention in the data.

  • Accessible corrections: editing customer and tax data within the system's workflow.
  • Data quality: validation before another processing attempt.
  • Clearer diagnosis: specific integration messages instead of a generic failure.
  • Operational continuity: form data retained after errors.

The main lesson was to follow the operation end to end: a usable interface, a valid contract, consistent data and a correctly interpreted external response must work together.

This case study is based on the project's technical account. Outcomes are qualitative; the available material contains no measured percentages, volumes or time savings.
